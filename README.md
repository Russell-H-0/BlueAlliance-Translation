## 目录

| 路径 | 放什么 | 谁看 |
|---|---|---|
| `drafts/` | 待审与成品译稿：一篇一个 `.md` + 同名 `.docx`，外加 `..._审核包.docx`（带审校要点的校对版） | 成员主要看这里 |
| `review-inbox/` | 返稿区：`docs/` 收改过的 Word，`notes/` 收纯批注 md | 校对 |
| `published/` | 已发布稿件的专区链接与回填数据 | 回溯 |
| `glossary.csv` | 译名与术语统一表（球员、规则、数据、战术），随时可补 | 全体 |
| `WORKFLOW.md` | 工作手册 | 全体 |
| `REVIEW-GUIDE.md` | 校对岗一页说明 | 校对 |
| `skills/ba-git-sync/` | 同步技能：只负责拉稿、命名、提交、开 PR，不审内容 | 用 agent 的成员 |
| `.github/` | 提交守卫：拦 `_ops/`、`sources/` 混入与返稿命名不合规 | 无需关心 |

> 原文全文**不在仓库里**（版权原因）。每篇稿件 `.md` 的头部都带原文标题、作者、媒体、发布时间和链接，校对时点链接核原文即可。
> 选题打分表、热度数据、台账这些在维护者本地的 `_ops/`，不进仓库。

## 一份稿子要经过什么

```
选题扫描 → 打分与热度核对 → 全译 → 自校 → 出稿（drafts/）
        → 审核包（drafts/）→ 成员校对（review-inbox/）→ 返稿比对 → 终稿 → 发布（published/）
```

成员参与的是中间两段：拿到审核包校对、把改动交回来。选题和打分由维护者完成，依据会在每日推送里公布。

## 三条硬规矩

1. 数字、引语、作者观点必须能在原文找到，不添加原文没有的判断
2. 付费墙抓不到全文就只做摘要并标注，不硬凑
3. 发布前必须有真人校对，文末同时署译者和校对
